# Native administrative workspace networking

The operator-installed `agentor-incus-network-service.py` exposes only `POST /v1/admin-networks/ensure` and `/inspect` with the exact body `{ "workspaceId": "…" }`. The existing pinned mTLS client and request bounds apply. There is no generic network/config proxy, caller-selected owner, address, container, command, token, or deletion endpoint. Older host services without the pinned admin adapter reject these routes.

`incus-admin-network-policy.py` reads the dedicated global administrative record and bounded per-owner group records afresh, through no-follow regular-file reads. It rejects malformed authority, duplicate workspace identities, inconsistent group ownership, non-native intent, wrong installation, and incomplete native nonce/overlay identity. An unverifiable group authority file blocks admin network admission; ordinary worker startup is unaffected. Ensure rejects a pending native operation. Read-only inspection can verify pending lifecycle state without repairing it.

Legacy workspace/group IDs remain bounded opaque IDs (letters, digits, underscore or dash, up to 128 characters). Native instance names retain `agentor-admin-<id>` when DNS-valid and at most 44 characters; otherwise they use `agentor-admin-<sha256(id) first 30 hex characters>`. Identity labels always retain the original ID. Canonical volume names are `<native-name>-workspace` and `<native-name>-agents`; selected `agentor-persist-<UUID>` names are unchanged. The stock Incus workspace socket uses `49 + project bytes + instance-name bytes`, including its fixed path and device suffix. A 44-byte name fits the 107-byte Linux pathname limit with projects up to 14 bytes (including the 12/13-byte DR fixture projects). Runtime provisioning and host policy reject longer actual socket paths before allocating resources. Existing native records are never silently renamed or adopted.

Each admin has an installation/owner/group/workspace-derived `aa…` Incus bridge in the host default network namespace. The restricted worker project receives only that exact network name in its managed-NIC allowlist after policy and peer admission settle. Existing project restrictions and ordinary bridge entries are preserved. A private `/24` has host gateway `.1`, the pinned orchestrator at `.2`, and the single admin guest at `.3`; DHCP allocates only `.3`. IPv6 is disabled. The guest's sole `eth0` has an exact MAC/IP and all three Incus MAC/IPv4/IPv6 spoof filters enabled.

The orchestrator joins through an exact owned Docker **Internal** bridge wrapper over that Incus bridge, with IPv4 bridge assignment inhibited. Its small IPAM range reserves `.3` for Incus. The helper pins the current running orchestrator's full Docker ID and exact writable `/data` bind or named-volume source, and validates both endpoint views. Foreign Docker members, native/profile references, extra kernel ports, wrappers, or labels are rejected and retained for review; the helper does not forcibly disconnect or adopt them. No host socket, namespace, or arbitrary path is mounted into a guest.

Private admin networking requires Docker Engine **29.3.0 or newer with API v1.54 available**. Only its host-side Docker transport is pinned to `/v1.54`; the first controller inspection rejects an unsupported API before any Incus network, firewall, or Docker endpoint mutation. Docker introduced the endpoint MAC field in v1.44 but [did not apply it on network connect until v1.54](https://docs.docker.com/reference/api/engine/version-history/#v154-api-changes), released in [29.3.0](https://docs.docker.com/engine/release-notes/29/#2930). A v1.44 prefix or string `DriverOpts` MAC is not a compatibility fix. Exact MAC/IP and both membership checks remain mandatory; an existing mismatched endpoint is retained for explicit operator reconciliation, never disconnected or adopted automatically.

Host filtering is explicit rather than inferred from NAT:

- Same-bridge guest traffic reaches only the orchestrator's TCP 3000 and 3099, plus established replies to orchestrator-originated guest requests. The orchestrator can reach the guest's existing terminal/editor/desktop services. The bridge-family filter also blocks IPv6 and other unsolicited layer-2 traffic; ARP is limited to the exact endpoint MAC/IP identities.
- Host input allows only guest DHCP and gateway DNS. Other host services, including Incus/control ports, are denied.
- Guest internet egress uses the one explicit default uplink and excludes private, shared, loopback, link-local, reserved, multicast, and connected LAN prefixes. Other worker/admin bridges are denied. Return traffic requires established/related state from that uplink. Guest application policy remains an additional restriction.
- Two owned nft tables filter before ordinary Docker forwarding rules. Exact scoped `DOCKER-USER` accepts prevent Docker's later default DROP from breaking already-filtered traffic. Both nft families are syntax-checked, atomically added, and read back before any Docker attachment or project publication. Existing changed/foreign policy is never flushed or silently repaired.

The fixed response contains installation, workspace/owner/kind (and group when applicable), network/subnet/gateway, guest address/MAC, and the private management address. The core runtime must bind management MCP **only** to that address on 3099 and use the returned `http://<peer>:3000` and `http://<peer>:3099/mcp` URLs. It must re-admit before create/start and validate fresh ownership/lease/incarnation before trusting guest traffic. Host admission permits no profiles, raw configuration, extra NICs, or disks beyond the pinned pool's canonical root/workspace/agent-data volumes. The core remains responsible for canonical volume ownership and image provenance.

The server-owned admin profile requires `limits.memory=4GiB`, `limits.cpu=2`, and `boot.autostart=false`; callers cannot override these through network admission. Existing native ensure and start preparation re-admit the dedicated identity before read-only boundary checks, so missing host firewall state after reboot can be recreated through the same exact ownership/device/controller checks. Changed or foreign policy still fails closed. Host firewall state is not a substitute for runtime startup admission after reboot or daemon replacement. Host uplink/public-LAN changes require stopping affected admin compute and explicit policy reconciliation; changed rules fail inspection. Empty owned networks, endpoint wrappers, and firewall policy are retained on compute deletion or partial failures. There is no automatic destructive cleanup. Deployment that retains an old orchestrator endpoint must settle that exact endpoint before the replacement can be admitted.

The existing operator setup installs the helper and pins its storage pool and orchestrator container in the policy unit. This source change does not execute setup, alter boot/kernel settings, or modify any live host.

## Evidence and remaining acceptance

Owned temporary files and stub transports cover authoritative global/group identity, malformed/symlink/FIFO/bounded inputs, stale-record fences, exact VM/device admission, wrapper membership, lifecycle idempotence, failure-before-publication, read-only inspection, and firewall expression allow/deny cases. Real local TLS fixtures cover route dispatch and the existing exact-client/request-size boundary. Setup tests inspect generated units with all host operations stubbed.

On 2026-10-18 both actual global/group admins were transferred through four cold canonical-volume copies with full checksum and metadata comparison. Both completed normal Agentor Start/Stop, authenticated terminal command execution and editor/desktop HTTP access using native networking. Their original Docker sources remain stopped and retained.

Full browser interaction, management MCP execution, encrypted native DR, isolation/firewall matrices, DHCP/DNS/public-egress matrices, controller replacement and reboot recovery remain unverified. The owner deferred additional robustness cycles to [issue #13](https://github.com/candlelightner/agentor/issues/13) after migration. Use disposable fixtures for fault injection and retain production backup/keys/sources. A failed syntax/read-back/membership check remains an admission failure; do not widen rules to pass it.

Relevant upstream behavior: [Incus bridge configuration](https://linuxcontainers.org/incus/docs/main/reference/network_bridge/), [Incus NIC spoof protection](https://linuxcontainers.org/incus/docs/main/explanation/security/), [Docker bridge options](https://docs.docker.com/engine/network/drivers/bridge/), [Docker internal networks/IPAM](https://docs.docker.com/reference/cli/docker/network/create/), and [nftables bridge/inet hooks and expressions](https://www.netfilter.org/projects/nftables/manpage.html).

Selected persistent paths are derived from `nativeRuntime.selectedVolumeIds` and the exact runtime owner's bounded, no-follow `managed-volumes.v1.json`. Only attached native `persistent-path` records with canonical UUID volume names are eligible. Pending unseeded selections have no guest device; ready seeded selections mount at their validated target. Protected runtime and credential paths remain denied. The exact historical `/home/agent/.local/share` exception still requires the core's canonical Kilo-link proof before attachment/start; host network policy validates its metadata and device layout, not guest contents.

A durable `selectedOperation` binds one selected volume, copy operation and VM incarnation. Read-only network inspection permits its exact staging mount at `/run/agentor-volume-seed/<volume-id>` (or its absence during attachment/removal). The final canonical target is permitted only for a seeded volume, a stopped VM, and the explicit seed-only `canonical: true` receipt; both sides of that exact transition are checked. Device acknowledgements distinguish unknown, accepted and settled mutations, without replaying any operation. Network ensure/start is denied until the receipt settles, and while deletion is in progress. Every existing authority recheck also rereads selected records. No arbitrary source, host path, NIC, mount option or caller-provided device is accepted. Detached-volume migration/backup preservation belongs to the storage workflow; this host policy neither attaches nor deletes detached volumes.

Selected-volume policy tests use private temporary authority files and stubbed transports. Actual guest copy, Kilo-link content proof, migration/restore fidelity and host firewall/network acceptance remain separate integration checks.

## Administrative VM memory changes and host policy updates

The host policy checks the applied `nativeRuntime.memoryLimit`, with `4GiB` for older records. A saved desired `memoryLimit` never changes admission for existing compute. An explicit rebuild persists the new applied limit before creating the replacement VM; memory, ownership, storage and NIC checks remain exact.

Updating the orchestrator image does **not** update the separately installed root host policy. From the trusted checkout containing this fix, on the actual host, update the existing installation's helper using its private operator config:

```sh
sudo scripts/setup-incus-host.sh --update-policy \
  --config /etc/agentor/incus/<installation-uuid>/config.json
```

This copies the trusted host scripts and restarts their existing policy service, preserving the installed config, certificates, VM instances, canonical data and network resources. It skips package installation, image conversion and routing reconciliation. Use the actual installation UUID locally; do not publish the config or diagnostics. Update the orchestrator too, then refresh administrative status before deciding whether Start or Rebuild is needed. Do not remove storage or weaken identity/network checks to clear a rejection.

Status reads inspect the owned native VM without starting it or changing desired state. An unavailable or rejected identity produces an explicit error instead of reporting the saved desired `running` state. Admin cards open the confirmed administration controls rather than ordinary worker lifecycle endpoints. Docker/Incus identity quarantine is separate and remains enforced; it never authorizes deleting or adopting retained Docker containers.
